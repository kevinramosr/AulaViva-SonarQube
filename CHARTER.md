Propósito:
El propósito del equipo es desarrollar un MVP de AulaViva, una plataforma educativa SaaS multi-tenant
que permita a diferentes colegios gestionar de manera segura y aislada sus cursos, docentes y estudiantes,
incorporando un tutor basado en inteligencia artificial que entregue respuestas contextualizadas mediante RAG.

Misión:
Construir una silución educativa segura, escalable y fácil de utilizar que ayude a estudiantes, docentes, apoderados
y colegios a mejorar la experiencia de aprendizaje mediante herramientas digitales y un tutor IA contextualizando
a los contenidos de cada curso.


Objetivo:

Diseñar y desarrollar un MVP funcional de AulaViva que contemple: 

-Multi-tenancy real, manteniendo aislada la información de cada colegio. 
-Gestión de usuarios, cursos, docentes y estudiantes. 
-Control de acceso basado en roles (RBAC). 
-Evaluaciones autocorregidas con feedback. 
-Tutor IA basado en RAG. 
-Utilización de los contenidos específicos de cada curso para generar respuestas. 
-Panel de seguimiento para apoderados. 
-Una arquitectura preparada para soportar aumentos de demanda. 


Valores: 

1. Responsabilidad: Cada integrante se compromete con las tareas asignadas. 
2. Comunicación: Los problemas y bloqueos deben comunicarse oportunamente. 
3. Colaboración: Las decisiones importantes se discutirán como equipo. 
4. Calidad: El código y la documentación deben cumplir los criterios establecidos. 
5. Seguridad: Se protegerán los datos de los usuarios y especialmente la información de estudiantes. 
6.Transparencia: El estado de las tareas y problemas estará visible en el tablero Kanban. 
7. Aprendizaje continuo: Se utilizarán los errores y revisiones como oportunidades de mejora.


Reglas: 

>Todas las tareas deben registrarse como Issues en GitHub. 
>Cada integrante debe mantener actualizado el estado de sus tareas. 
>Los cambios de código se realizarán mediante Pull Requests. 
>Ningún cambio importante será incorporado sin revisión de otro integrante. 
>Las decisiones arquitectónicas relevantes serán registradas mediante ADR. 
>No se subirán contraseñas, tokens, claves API ni información personal al repositorio. 
>Los bloqueos deben comunicarse lo antes posible. 
>Las tareas deben tener criterios de aceptación claros. 
>Se respetará la opinión de los demás integrantes durante las decisiones técnicas. 
>Las funcionalidades terminadas deben cumplir la Definition of Done. 


Canal de comunicación:

El equipo utilizará como canal principal WhatsApp o Discord donde se comunicarán problemas generales, sobre el desarollo,
relacionados al tutor IAy RAG, problemas sobre el proyecto y decisiones tomadas.


Cadencia de reuniones: Se realizarán reuniones virtuales para hacer seguimiento, revisiones, planificaciones o retroalimentación
de funciones correctas o problemas respecto al proyecto, sino se realizan reuniones virtuales serán vias mensajes los acuerdos.


Definition of Done (DoD) 
Una tarea será considerada Done cuando: 

-[Control]La funcionalidad fue implementada. 
-[Control]Cumple los criterios de aceptación. 
-[Control]El código fue revisado mediante Pull Request. 
-[Control]Se realizaron las pruebas correspondientes. 
-[Control]No existen errores críticos conocidos. 
-[Control]La funcionalidad fue integrada correctamente al proyecto. 
-[Control]Se actualizó la documentación cuando sea necesario. 
-[Control]No se incorporaron credenciales ni información sensible. 
-[Control]El responsable de QA verificó la funcionalidad. 
-[Control]La tarea fue marcada como completada en el Trello. 


Política de uso de Inteligencia Artificial: 

El equipo podrá utilizar herramientas de inteligencia artificial como apoyo durante el desarrollo del proyecto. 

Usos permitidos:

-Generación de ideas. 
-Apoyo en programación. 
-Explicación de código. 
-Detección y resolución de errores. 
-Generación de pruebas. 
-Apoyo en documentación. 
-Investigación de alternativas técnicas. 
-Generación de borradores que posteriormente serán revisados por el equipo. 


Reglas:

1. Todo código generado mediante IA debe ser revisado por un integrante antes de incorporarlo al proyecto. 
2. La responsabilidad final del código corresponde al equipo. 
3. No se ingresarán contraseñas, tokens, información personal de estudiantes ni datos sensibles en herramientas externas. 
4. Las respuestas generadas por IA deben ser verificadas antes de utilizarse. 
5. Las decisiones arquitectónicas importantes no serán tomadas exclusivamente por una IA. 
6. El uso de IA debe quedar registrado cuando sea relevante para una decisión o funcionalidad. 
7. El tutor IA de AulaViva deberá utilizar mecanismos RAG para entregar respuestas basadas en fuentes y contenidos autorizados.
